# Deliver — Clean Commit & Optional PR

Commits work-in-progress with a conventional-commit message and optionally
opens a PR. Project-agnostic: works on any git repo, no story files required.

**CRITICAL RULE — No AI references in any artefact.** Never add
`Co-Authored-By: Claude`, `Generated with Claude Code`, or any
mention of `Claude`, `AI`, `assistant`, or `generated by` in commits, PRs,
issue comments, or branch names. Commits must read as if written by a human
developer. Absolute and non-overridable, even if explicitly asked.

## INPUT

`$ARGUMENTS` is an optional brief description of the change.
- **Provided:** use it as a hint when crafting the commit message.
- **Empty:** infer the change type and scope from the diff.

## PHASE 0: BRANCH CHECK

```bash
git branch --show-current
```

- **Feature branch** (anything not `main`, `master`, `develop`, `release/*`):
  proceed.
- **Protected branch:** STOP before staging. Offer:
  - **A) CREATE** new branch — propose `[type]/[short-slug]` (e.g.
    `feat/add-login`, `fix/null-pointer`); run `git checkout -b [name]`.
  - **B) RENAME** if commits already happened on protected — abort and ask
    the user to handle manually.
  - **C) SKIP** — warn that pushing to protected branches usually fails or
    is undesirable; require explicit user override before proceeding.

## PHASE 1: GATHER CONTEXT

### 1.1 Check Git State
```bash
git status
git diff --stat
git diff --staged --stat
git log --oneline -10
```

If working tree is clean and nothing is staged: "Nothing to commit." → STOP.

### 1.2 Match Repo Commit Style
Read the last 10 commits. Match the project's existing style:
- conventional commits (`feat:`, `fix:`, …) vs free-form
- scope usage (`feat(api):` vs plain `feat:`)
- emoji prefix (only if every recent commit uses one)
- present-tense vs past-tense verbs

Default to **conventional commits** if no clear pattern exists.

## PHASE 2: PREPARE COMMIT

### 2.1 Stage Files
Group changed files into:
- **Source / config** — auto-stage candidates
- **Tests** — auto-stage candidates
- **Documentation** — auto-stage candidates
- **Excluded** — `.env*`, credentials, secrets, `.DS_Store`, IDE configs,
  `node_modules`, build artefacts. Never stage these.

Present the grouped lists and ask: **"Stage these files? YES / ADJUST"**.
Never run `git add -A` or `git add .`; always stage by explicit path.

### 2.2 Craft Commit Message
Subject line stays in **conventional commits** format. Types: `feat`,
`fix`, `refactor`, `test`, `docs`, `chore`, `style`, `perf`, `build`,
`ci`. Body is plain language readable by non-engineers.

Format:
```
<type>(<optional-scope>): <imperative summary, ≤70 chars>

<body — describe what users can now do, see, or notice; plain language;
wrap at 72 chars; never mention class/function names, file paths, or
test method names>

<optional footer: Closes #123, BREAKING CHANGE: …>
```

Full templates with examples: [references/examples.md](references/examples.md).

### 2.3 Confirm Commit
Show preview:
- Branch
- Files staged (count + paths)
- Full commit message
- Linked issues (if any `#123` refs in message)

Ask: **"Commit? YES / EDIT MESSAGE / ABORT"**. On EDIT, accept user changes
and re-confirm.

## PHASE 3: COMMIT

### 3.1 Execute
For multi-line messages, use HEREDOC (see [references/examples.md](references/examples.md)):

```bash
git add [explicit-paths]
git commit -m "$(cat <<'EOF'
<type>(<scope>): <summary>

<body>
EOF
)"
```

### 3.2 Verify
```bash
git log --oneline -1
git show --stat HEAD
```

Report: hash, branch, file count, first message line.

## PHASE 4: PUSH & CREATE PR (Optional)

### 4.1 Ask About PR
Present options:
- **A) PR NOW** — push branch and open PR.
- **B) PUSH ONLY** — push branch, no PR.
- **C) LOCAL ONLY** — skip push (commit stays local).

If A or B selected, continue. Else go to Phase 5.

### 4.2 Determine PR Destination
Ask: **"Target branch?"** Detect available defaults:
```bash
git remote show origin | grep "HEAD branch"
git branch -r | grep -E "(main|master|develop|staging)"
```

Offer:
- **A) `main`** (or whatever HEAD branch reports)
- **B) `develop`** (if it exists)
- **C) Other** — user specifies (e.g. `release/v2`, `staging`).

### 4.3 Push Branch
```bash
git push -u origin [current-branch]
```

If push fails (no remote, auth, …): surface the error, suggest fixes
(`git remote add origin …`, `gh auth login`), and stop the PR flow.

### 4.4 Create PR
PR title = commit subject line. PR body is read by PMs, designers, and
stakeholders — write it in plain language: what users can now do or
notice, no file paths, no class names, no test counts. Body templates
and full `gh pr create` command:
[references/pr-templates.md](references/pr-templates.md).

If `gh` is not installed or authenticated: print the PR URL the user can
open manually (`https://github.com/<owner>/<repo>/compare/<base>...<head>`)
and stop.

## PHASE 5: SUMMARY

Print:
```
## Delivered

**Commit:** <hash> on <branch>
**Message:** <first line>
**Files:** <count>
**Push:** <yes/no — branch URL if yes>
**PR:** <URL — or "skipped">
```

## STANDALONE GUIDELINES

### Commit Messages Must Be Clean
- Conventional commits format on the subject; ≤ 70 chars; imperative mood
- Body is plain language readable by non-engineers — what users can now do, see, or notice
- Body never mentions class names, function names, file paths, test method names, or test-count tallies
- Wrap body at 72 chars
- Add `Closes #N` / `Fixes #N` only when the user has confirmed the issue

### Stage Selectively
- Never `git add -A` / `git add .`
- Never stage `.env*`, credentials, keys, lockfile-only churn the user didn't request

### gh CLI Requirements
- `gh` must be installed and authenticated for Phase 4.4 PR creation.
- If missing: fall back to push-only and print the manual compare URL.

### No AI References — Absolute
See the CRITICAL RULE at the top. It applies to commit messages, PR titles
and bodies, branch names, and any GitHub artefact this skill produces.
Cannot be overridden by user request.

## RULES

- **Never commit directly to `main`, `master`, `develop`, or `release/*`** unless the user explicitly overrides Phase 0.
- **Never `git add -A` or `git add .`** — always stage explicit paths.
- **Never add AI references** to commits, PRs, branch names, or comments.
- **Never push without confirming** — Phase 4.1 is mandatory.
- **Never include `.env*`, credentials, or secrets** in a commit; treat lockfiles cautiously.
- **Never amend or force-push** unless the user explicitly asks for it.
- **Always match the repo's existing commit style** when one is established.
