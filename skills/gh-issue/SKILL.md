# gh-issue — Single GitHub Issue (Optional Project)

Creates one GitHub Issue from free-text intent or a story file, with optional
add to a GitHub Project. Project-agnostic. Mirrors `gh issue create` flag style.

**CRITICAL RULE — No AI references in any artefact.** Never add
`Co-Authored-By: Claude`, `Generated with Claude Code`, or any
mention of `Claude`, `AI`, `assistant`, or `generated by` in the issue title,
body, labels, or any project metadata. Issues must read as if written by a
human developer. Absolute and non-overridable, even if explicitly asked.

Issue body templates and label conventions:
[references/templates.md](references/templates.md).

---

## INPUT

`$ARGUMENTS` is a free-form title-or-description plus optional flags:

| Token | Meaning |
|---|---|
| Free text | Title (≤ 70 chars) — or a brief description used to draft the title |
| `--story <path>` | Path to a story file (ck-code/ck-tools format) used as authoritative content for the body |
| `--project <number>` | Add the created issue to this GitHub Project (number from `gh project list`) |
| `--label <name>` | Apply this label (repeatable). Only labels that already exist in the repo. |
| `--assignee <user>` | Assign to this GitHub username. |

If `$ARGUMENTS` is empty and no `--story` flag, ask the user for a title via
`AskUserQuestion` (single question — never more).

---

## PHASE 0: VALIDATE ENVIRONMENT

```bash
gh auth status
gh repo view --json nameWithOwner -q .nameWithOwner
```

If either fails, stop and tell the user what to fix.

If `--project <N>` is provided, validate it exists:
```bash
gh project view <N> --owner @me --format json
```

On failure, surface the error and ask whether to continue without project
assignment or abort.

---

## PHASE 1: GATHER INTENT

Three branches based on input:

### 1.1 Story-driven (`--story <path>` provided)
1. `Read` the story file.
2. Extract:
   - **Title** — from the `# Story:` heading or `# Story <ID>:` heading.
   - **Description** — body up to the first H2.
   - **Acceptance Criteria** — entire `## Acceptance Criteria` section.
   - **Files Touched** — `## Files Touched` section, if present.
   - **Mode** — from the metadata block (FEATURE / FIX / REFACTOR).
3. Map Mode to a default label suggestion (per
   [references/templates.md](references/templates.md) label table). Only
   suggest; do not auto-apply.

### 1.2 Title-driven (positional arg only)
1. Treat free text as the issue title (truncate to 70 chars; suggest a shorter
   form if longer).
2. Ask **at most one** clarifying question via `AskUserQuestion` covering
   description + label preference. Skip if obvious from the title.

### 1.3 Empty input
1. Ask for the title via `AskUserQuestion`.
2. Then drop into the title-driven branch.

In all branches, never invent labels or assignees that don't exist. To list
existing labels:
```bash
gh label list --limit 100 --json name -q '.[].name'
```

---

## PHASE 2: CONFIRM

Build a preview block:

```
## Issue to Create

**Repository:** <owner/repo>
**Title:** <title>
**Labels:** <comma-separated, or "none">
**Assignee:** <user, or "none">
**Project:** <name + number, or "none">
**Body preview:** (first ~15 lines)
<excerpt>

Proceed? YES / NO / EDIT
```

- **YES** — go to Phase 3.
- **NO** — abort cleanly. No tool calls beyond this point.
- **EDIT** — accept user adjustments to title / body / labels / assignee /
  project, then re-show the preview and re-ask.

If `--project <N>` was **not** provided and `gh project list --owner @me
--format json` returns ≥ 1 project, ask **one** extra yes/no question:

> Add this issue to a GitHub Project? (y/N)

If yes, list available projects and ask the user to pick one. If the user
declines or no projects exist, skip Phase 4.

---

## PHASE 3: CREATE ISSUE

```bash
gh issue create \
  --title "<title>" \
  --body "$(cat <<'BODY'
<final body>
BODY
)" \
  [--label "<name>" --label "<name2>"] \
  [--assignee "<user>"]
```

Capture the issue URL and number from stdout. On failure (validation,
permissions, rate limit), surface the error and stop — do not retry blindly.

---

## PHASE 4 (OPTIONAL): ADD TO PROJECT

Only runs if Phase 2 confirmed a project (via flag or interactive opt-in).

```bash
gh project item-add <project-number> --owner @me --url <issue-url>
```

If this fails (project not found, no permission), report the error but **do
not** roll back the created issue. The issue exists; project assignment is a
best-effort follow-up.

---

## PHASE 5: SUMMARY

Print:

```
## Issue Created

**URL:**     <issue-url>
**Number:**  #<n>
**Repo:**    <owner/repo>
**Project:** <name #N — or "skipped">
**Labels:**  <comma-separated, or "none">
```

Add one next-step suggestion:
- If invoked with `--story`: "Reference this issue from the story's commit
  (`Closes #<n>`) when the work ships."
- Otherwise: "Run `/ck-tools:deliver` once the work is committed to link
  `Closes #<n>` in the commit message."

---

## RULES

- **Never auto-commit, push, or merge.** This skill only touches GitHub
  Issues / Projects, not the working tree.
- **Never invent labels, assignees, or project numbers** — verify each via
  `gh label list`, `gh api users/<user>`, or `gh project list` first.
- **Never create more than one issue per invocation.** For batch creation
  from `tasks/`, the user wants `/ck-code:to-issues` instead.
- **Never add AI references** to the title, body, comments, or any project
  metadata. The CRITICAL RULE at the top is absolute.
- **Never call `gh issue create` or `gh project item-add` without an explicit
  YES from Phase 2.**
- **Never roll back a created issue if Phase 4 fails** — report the project
  error and let the user resolve it manually.
- **Never ask more than 2 clarifying questions total** (Phase 1 + Phase 2
  combined). If more clarity is needed, ask the user to re-run with `--story`.

---

## QUICK REFERENCE

| Situation | Action |
|---|---|
| Invoked with `--story <path>` | Phase 1.1 — extract title, body, ac, files. Suggest label from Mode. |
| Invoked with positional title only | Phase 1.2 — at most one clarifying question. |
| Invoked empty | Phase 1.3 — ask for title interactively. |
| `--project <N>` flag absent, projects exist | Phase 2 asks one yes/no opt-in question. |
| `gh project view` fails for `--project <N>` | Ask whether to continue without project or abort. |
| `gh project item-add` fails after issue creation | Report error; issue stays; user resolves project manually. |
| User answers NO at Phase 2 | Abort cleanly — no `gh` mutations. |
